# 職員管理と事業所・権限管理の氏名不一致修正

作業日：2026年11月13日。開発ブランチ：`fix/staff-name-consistency`。
起点：本番 `main` の `3376f2eca27453bdd5b1deb5d61cfa1626da95cd`（PR #18反映後）。
本番への反映・DB変更・マージは未実施。追加の有料サービスは使用しない。

## 原因と調査

「氏名未設定」は職員管理の表示処理で作られた仮名ではなく、`organization_staff.staff_name` に残った値だった。`supabase/attendance_setup.sql` の初期追加、および `staff/index.html` / `admin/index.html` のログイン職員追加が、当時メンバー名が空の場合にこの値を保存する。

その後、本人がトップやAI記録で氏名を登録しても、更新先は `organization_members.staff_name` だけだった。職員マスターへ同期するトリガーは存在しなかった。また職員管理での名前変更は逆に職員マスターしか更新していなかったため、どちらの方向でも不一致が残る。

| 対象 | 変更前の参照・保存先 | 修正後 |
| --- | --- | --- |
| 職員管理 | `organization_staff.staff_name` を取得・更新 | 共通ビューで取得、管理者RPCで正しい保存元へ更新 |
| 事業所・権限管理 | `list_organization_staff` RPC → `organization_members.staff_name` | 保存元・権限処理を維持。画面復帰時に再取得 |
| トップ・AI記録の本人登録 | 本人・施設の `organization_members.staff_name` | 既存処理を維持。DBトリガーで対応するマスターの氏名も同期 |
| 管理画面の一覧、今日の担当の未入力一覧、出勤簿、今後の担当割当 | 職員マスターの古い氏名 | 同じ共通ビューで現在の氏名を取得 |
| ログインなし職員 | `organization_staff.staff_name` | 保存元を維持 |

本番ではメタデータ、制約、RLS、GRANT、関数、集計のみを読み取り確認した。氏名そのものは調査のために取得していない。職員45行、ログイン紐付け26行、正しい登録名に対してマスターが「氏名未設定」の行1件、氏名が不一致の行は計5件。施設・認証ユーザーの対応先が存在しない行は0件だった。テストによる本番への書き込みはない。

## 修正した処理とファイル

- `supabase/migrations/20261113013000_staff_name_consistency.sql`：承認後に適用するDB変更案。共通の読み取り専用ビュー、管理者用改名RPC、今後の変更を同期する内部トリガーを追加。既存行のバックフィル、削除、一括UPDATEは行わない。
- `staff/index.html`：共通ビューを取得し、改名RPCを使用する。読み込み失敗・本人IDの不整合時は古い操作一覧を消してエラーを表示する。保存結果の職員ID・施設ID・認証ユーザーID・氏名を検証する。
- `manage/index.html`：氏名の保存元は従来のまま、画面復帰時に再取得する。施設切替前の遅い応答が別施設の一覧を置き換えないよう確認する。
- `admin/index.html`、`dashboard/index.html`、`attendance/cloud.js`、`assignment/offline-staff-addon.js`：氏名を使う職員取得を共通ビューへ変更する。IDだけの権限判定・件数取得や既存の書き込み先は維持する。
- `attendance/index.html`、`assignment/index.html`：変更したスクリプトのキャッシュ識別子を更新する。
- `tests/staff_name_database.cjs`、`tests/fixtures/staff_names_schema.sql`：隔離Postgresで新しいSQLを実行するテスト。
- `tests/nexia_browser.cjs`、`tests/attendance_dom.cjs`、`tests/html_inline_syntax.cjs`、`.github/workflows/safety-check.yml`：画面・回帰検証とCIを更新する。CIから本番DBへ接続・マイグレーション適用は行わない。
- 本文書と `docs/staff-name-registration.md`：原因、変更範囲、テスト、承認後の注意点を記録する。

ログイン職員の正しい保存元は `organization_members.staff_name`。紐付けは `organization_staff.organization_id = organization_members.organization_id` **かつ** `organization_staff.linked_user_id = organization_members.user_id` の両方で行う。同姓同名、メールアドレス、職員一覧の順番、localStorageの名前、認証メタデータから本人を推定しない。職員IDと認証ユーザーIDは別のIDとして扱う。

共通ビューは `security_invoker=true` とし、既存テーブルのRLSに従う。ビューにはSELECTだけを許可する。既存のRLS・GRANT・所属・権限は変更しない。新しい公開RPCは `SECURITY INVOKER`、権限を持つ実装とトリガーはprivateスキーマ内に置き、`search_path=''` を指定する。

改名RPCはログイン状態・対象施設の管理者権限・施設の稼働状態をサーバーで確認する。施設＋職員IDで対象を取得し、認証ユーザーIDと変更前の氏名も一致する場合だけ改名する。本人登録と同じ順序で行ロックを取得し、古い画面による上書きを拒否する。職員ID・所属・役割・本人紐付け・勤務記録は変更しない。

今後、本人が名前を登録・変更すると、対応する施設＋認証ユーザーのマスターだけを同期する。古いクライアントがログイン職員のマスターだけを直接改名しようとした場合は明示的に拒否する。紐付け追加時は正しい氏名を取得し、所属解除時は最後の登録名を保持してから既存FKがログイン紐付けを外す。
