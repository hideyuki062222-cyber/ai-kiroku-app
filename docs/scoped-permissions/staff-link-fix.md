# PR #28：管理者の職員追加・本人紐付けの互換性修正

本番SQL適用、mainへのマージ、公開・デプロイは未実施です。この修正は未適用のPR #28内で準備します。旧PR #26は変更せず、両方のSQLを適用しません。

## 原因

職員管理の「新しいログイン利用者を職員に追加」は、既存の認証アカウントと所属情報を参照して `organization_staff` に複数行をINSERTします。「本人紐付け・所属」は、既存の職員IDの `linked_user_id` 等をUPDATEします。新しい認証アカウントを作成する処理ではありません。

PR #28で変更した `private.canonicalize_linked_staff_name()` は、他人の職員情報を操作するときの条件を「staff_info権限があり、同じ施設・同じ本人IDのUPDATE」に限定していました。この委任職員向けの制限が管理者にも適用され、RLSでは許可された管理者のINSERTや本人紐付け変更まで `admin_required` で拒否していました。

移行前は成功、旧PR #28では失敗することを架空データで再現しています。今回追加した回帰試験も、修正前のSQLでは `admin_required` を検出します。

## 修正

- 対象施設の管理者は、従来どおりログイン職員の追加・本人紐付け・解除・再紐付けを実行できます。
- `staff_info` の委任職員は、同じ施設・同じ本人IDの表示情報更新だけを実行できます。本人紐付け、所属施設ID、基本role、機能権限を変更する権限は追加しません。
- 認証ユーザーIDは引き続き `auth.uid()`、管理者はDBの `organization_members` で判定します。氏名や利用者が編集できるJWTメタデータを権限判定に使いません。
- トリガー関数の既存のSECURITY DEFINER、空のsearch_path、実行権限の制限を維持します。RLS・外部キー・本人IDの一意制約・Authのアカウント管理は変更しません。
- INSERTでは委任条件のOLD行を参照しないよう、操作種別の検査を分けました。

変更するSQLは未適用の `20261120051058_safe_granular_facility_permissions.sql` の関数本体のみです。追加のデータ移行・履歴の書換えはありません。

## 職員管理の検証

`tests/scoped_staff_management_database.cjs` の60項目を、PGliteおよび実際のPostgreSQL 17.11で合格しました。すべて架空データです。

| 操作 | 期待する結果 |
|---|---|
| 管理者のログイン職員一括追加 | 成功。所属と認証ユーザーIDで正しい氏名を取得 |
| 管理者のログインなし職員追加・本人紐付け | 成功。同じ職員IDを維持 |

### 「所属施設変更」の確認範囲

既存画面の「所属表示」は文字列 `office_label` です。これを変更しても、実際の所属施設IDや所属権限は変わりません。

実際の施設IDの変更についても、既存のRLSのUSINGとWITH CHECKが、変更元・変更先の両方を検査することを確認しました。片方の施設だけの管理者、一般職員、委任職員の操作は拒否します。両施設の管理者が、関連業務データのない架空職員行を変更する既存DB操作は成功します。出勤簿等に紐付く職員の施設ID変更は外部キーで拒否され、過去記録の関連を壊しません。

今回、職員の施設間移動画面や認証アカウントを別施設へ自動登録する機能は追加していません。

## 画面と他機能

`tests/scoped_permissions_browser.cjs` に、実際の `staff/index.html` を使う以下の操作を追加しました。PC1440px・スマホ390pxで合格しました。

1. ログインなし職員の追加
2. 既存のログイン職員への本人紐付け、所属表示・雇用区分の保存
3. 再読み込み後の紐付け・表示の維持
4. 紐付け解除、氏名変更
5. ログイン職員の一括追加
6. 一般職員による職員管理URLへの直接アクセスの制限
7. 従来の差分権限保存・競合・解除・編集・CSV/PDF出力

テスト用RESTアダプターは、Supabase SDKの複数行INSERTの `columns` パラメーターとTABLEを返す氏名変更RPCを正しく扱うよう補いました。権限・RLSは隔離DBの実際の関数とポリシーで検証します。アプリ本体の職員管理画面やログイン処理を、テストに合わせて書き換えることはしていません。

移行前後の30表を全値比較し、職員管理操作の前後でもAI記録・申し送り・担当割当・食事・出勤簿・金銭出納帳・既存履歴が変わらないことを確認しました。氏名変更によって、元の担当割当や記録に保存された当時の職員名を一括上書きしません。
