## バックアップと復元を先に確認する

1. 安全な保管先と復号情報の管理者を決める。現在の作業環境だけを唯一の保管先にしない。キー・パスフレーズをリポジトリや会話へ貼らない。
2. 対象データと搬出先の許可を確認する。既存の許可はNEXIAの権限・職員・利用者・記録・申し送り・割当・食事・出勤簿・出納帳と関連履歴、参照に必要なAuth UUIDのみ。採用管理・独立した食事システム・パスワード・トークンは対象外。
3. `tools/scoped-backup-metadata.sql` は読取り専用の定義取得。`tools/scoped-backup-query.py` は公開鍵を使うSELECTを作るだけで実行しない。実行する際もSELECTに限り、DB側で暗号化した結果だけを保存する。未知の秘密らしい列があれば生成を拒否する。
4. 暗号化ファイル取得時にSHA256を別途記録し、ファイルを600、保管ディレクトリを700にする。復号用情報は別に保管する。
5. 本番接続を持たない `tools/scoped-backup-restore.cjs` で、隔離PGliteへ復元・照合・新SQLのリハーサルを行う。入力ハッシュが違えば復号前に拒否する。対象外スキーマは定義のみ、AuthはUUIDスタブだけで、Supabase全体の復旧ではない。

保護ディレクトリはリポジトリ外の絶対パスで指定します。実際のハッシュは安全な記録から設定し、DB URL・サービスキーは渡しません。

```sh
NEXIA_BACKUP_DIR=/protected/backup \
NEXIA_BACKUP_SHA256='取得時に記録した64桁のSHA256' \
PGLITE_PATH=/installed/node_modules/@electric-sql/pglite \
node tools/scoped-backup-restore.cjs
```

ツールはローカルメモリ上のDBだけを使います。復号した実データを平文ファイルやログに保存しません。結果は保護ディレクトリの `restore-report.json` に件数・値のハッシュ等として出力します。有料PITRや有料ブランチは使いません。

## 将来、承認された場合の反映順序

1. 旧PR・本PR・mainの最新SHAとCIを確認。SQLのSHA256を報告と照合する。旧SQLと新SQLを混在させない。
2. 本番定義の差分と既存料金・所属・旧enabledを読み取り確認。変更があれば適用せず調整する。直前のバックアップ・隔離復元・安全な別保管を完了する。
3. 権限設定を行わない時間を決め、古い権限設定タブを閉じるよう運用担当へ案内する。通常の記録・提供入力は維持するが、所属等のSHAREロックにより書込みが短時間待つ可能性がある。
4. 承認済みの実行手段が新規トランザクションでSQLを実行できることを隔離環境で確認する。既にSELECT等を行った外側のトランザクションでは、REPEATABLE READを保証できず中止する設計。設定を外して強行しない。
5. 新SQLを1トランザクションで適用。ロック待ち5秒、実行上限120秒。不一致・競合・タイムアウトなら全体をロールバックし、原因を確認して再承認の範囲を判断する。
6. `supabase/checks/20261120051058_verify_facility_permissions.sql` で、旧4機能、追加権限0、管理者・通常職員の判定、新表のRLS・直接書込み禁止・anon RPC禁止を読み取り確認する。実職員へ検証用権限を勝手に付与しない。
7. 同じ承認対象のフロントをmainへマージし、既存GitHub Pagesで公開する。SQL先行・画面後行。新RPCは `p_changes` なので旧PR #26の画面を混ぜない。公開ファイルのSHAと公開処理成功を確認する。
8. 管理者画面を再読み込みし、必要な権限だけ明示設定する。料金・請求確定・所属・ログイン権限は別操作。チェックをすべてONにしても管理者にはならない。

## 失敗時・公開後の復旧

- SQL途中の失敗：トランザクション全体をロールバックする。既存表のデータを復元名目で上書きしない。新表の二重作成を回避するため実際の移行履歴・表の有無を先に確認する。
- 適用後の封じ込め：別承認を得て `supabase/rollbacks/20261120051058_permission_compatibility.sql` を使う。権限変更RPCと拡張操作を停止し、保存済みの権限行・業務データ・訂正・監査履歴を残す。旧4機能は実際の機能別行に応じて維持する。単なる旧enabledフラグ判定に戻すと過剰付与になるため禁止。
- 不具合解消後の復帰：別承認で `supabase/rollbacks/20261120051058_restore_permission_functions.sql` を使う。新しい差分RPC・権限判定・旧RPC互換処理を復帰し、保存済み行は再作成しない。復帰後の新規保存・解除を隔離DBで試験済み。
- UIの切り戻し：訂正履歴が作られた後に、訂正を無視する古い記録履歴画面へ戻してはいけない。旧PR #26の全置換p_permissions画面にも戻さない。保存失敗時は入力を保持し、版を読み直す。
- DB全体復元：バックアップ後の正常な実記録を失うため最終手段。差分データの保全・停止時間・Auth/Storage等の別復旧手順を含め、別途承認が必要。今回のコードが自動で本番へ復元・初期化することはない。
